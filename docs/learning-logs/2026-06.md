### 理解の証明

#### `0.0.0.0` vs `127.0.0.1`
- 理解内容: `0.0.0.0` は全ネットワークインターフェースで待機、`127.0.0.1` はループバックのみ
- 判断基準: コンテナ外からアクセスするには `0.0.0.0` が必須
- 実装での選択理由: Docker Composeでホストからアクセスするため

#### `async/await` + `try/catch`
- 理解内容: `app.listen()` 失敗時にエラーをキャッチしてプロセスを明示的に終了する
- 判断基準: catchしないとエラーが握りつぶされる可能性がある
- 実装での選択理由: ポート競合等の起動失敗を確実に検知するため

#### `logger: true`
- 理解内容: JSON形式でログを標準出力する
- 判断基準: Datadog・Grafana Loki等のログ収集ツールがJSON形式を自動パースできる
- 実装での選択理由: 将来のminikubeデプロイ時の運用を見据えて

### トラブルシューティング
- `docker compose restart` ではマウントが更新されない → `down → up` が必要
- 名前付きボリュームはコンテナ再作成でリセットされる → `npm install` が必要

## Issue #26: エラーハンドリング（404・バリデーション）

### やったこと
- `GET /posts/:id` で存在しないIDの場合404を返す
- `POST /posts`, `PUT /posts/:id` でtitle・content未入力の場合400を返す

### 理解の証明

#### `!title` がtrueになる条件
- 理解内容: `title` が `undefined`（キー自体が無い）または空文字 `""` の場合に `true` になる
- 判断基準: 「未入力」と「キーが無い」を一括でチェックできる
- 実装での選択理由: リクエストボディの両方のパターンに対応するため

#### 400 vs 404の使い分け
- 理解内容: 400はリクエスト自体が不正、404はリクエストは正しいがデータが存在しない
- 判断基準: バリデーションエラーは400、存在しないIDへのアクセスは404
- 実装での選択理由: HTTPステータスコードの意味に従い、クライアント側が適切にハンドリングできるようにする

#### バリデーションをDB操作前に行う理由
- 理解内容: 不正なデータの保存を防ぎ、無駄なDBアクセスのコストを避ける
- 判断基準: アプリ側でチェック可能なものは先にチェックする
- 実装での選択理由: DB層に依存しないエラーハンドリングを実現

### トラブルシューティング
- コンテナ再作成後、テーブルが消えていた → `cd /workspace && npx prisma migrate deploy` で復旧

## Issue #27: Swaggerスキーマ定義

### やったこと
- 全エンドポイントに `schema` オプション（body・params）を追加
- Swagger UIで「Try it out」のフォーム表示・実行を確認
- `schema` のバリデーションが機能するため、手書きの `if (!title || !content)` を削除
- DBボリュームのマウント先パスが間違っていた問題を修正（`/var/lib/postgresql/postgres_data` → `/var/lib/postgresql/data`）

### 理解の証明

#### `schema`とFastify標準バリデーションの関係
- 理解内容: `schema` はFastify本体の機能（JSON Schemaベースのバリデーション）で、`@fastify/swagger`がそれを読んでドキュメント生成している
- 判断基準: `schema`単体でもバリデーションは機能する。Swaggerを外しても無駄にならない
- 実装での選択理由: 1つの定義でバリデーションとドキュメントの両方を満たせる

#### 手書きバリデーションが不要になった理由
- 理解内容: `schema.required`がリクエスト到達前にチェックされ、400を返すため、後続の`if`文は到達不可能（デッドコード）になる
- 判断基準: 実際にcurlで確認し、`FST_ERR_VALIDATION`のエラーが返ることを確認した
- 実装での選択理由: 重複したバリデーションロジックを削除し、保守性を向上

#### `schema`で表現できないチェック（404判定）
- 理解内容: `schema`は「リクエストの形式」を検証するもので、「DBにデータが存在するか」という実行時の状態は検証できない
- 判断基準: 形式チェック（schema）とビジネスロジック（DB存在確認）は別レイヤー
- 実装での選択理由: `if (!post)`による404判定は手書きロジックとして残す

### トラブルシューティング
- DBデータがコンテナ再作成時に消える問題 → `docker-compose.yml`のDBボリュームマウント先が `/var/lib/postgresql/postgres_data`（誤り）になっていた。正しくは `/var/lib/postgresql/data`。修正により永続化された

## Issue #31: blog-frontend 編集フォーム実装（PUT /posts/:id）

### やったこと
- `app/posts/[id]/edit/page.tsx` を作成
- 既存データを `defaultValue` で初期値として表示
- `bind` を使ってServer ActionにidをURL非公開で渡す
- `published` チェックボックスを追加

### 理解の証明

#### `bind(null, id)` の使い方
- 理解内容: 第一引数の `null` は `this` の値。今回は不要なのでnull
- 判断基準: bindで束縛した値が第一引数、formDataが最後の引数として自動で渡される
- 実装での選択理由: hiddenフィールドと違いHTMLに値が露出しないためより安全

#### `defaultValue` vs `value`
- 理解内容: `value` はReactのstateと同期が必要（制御コンポーネント）、`defaultValue` は初期値だけ設定してブラウザに任せる（非制御コンポーネント）
- 実装での選択理由: Server Actionと組み合わせる場合は `defaultValue` がシンプル

#### HTMLフォームのPUT制約の回避
- 理解内容: HTMLの `<form>` はGET/POSTのみサポート
- 実装での選択理由: Server Action内でfetchを使って明示的に `method: 'PUT'` を指定

## Issue #33: バックエンドテスト（Vitest）

### やったこと
- Vitestを導入
- `index.ts` を `buildApp()` でリファクタリング（起動と構築を分離）
- `require.main === module` でテスト時に `start()` が実行されないように修正
- `vitest.config.ts` で `DATABASE_URL` を設定
- `src/__tests__/posts.test.ts` に全エンドポイントのテストを実装
- `createTestPost` / `deleteTestPost` ヘルパー関数でテストデータを管理

### 理解の証明

#### `require.main === module` の意味
- 理解内容: ファイルが直接実行された場合のみ `start()` を実行する（Pythonの `if __name__ == '__main__':` と同じ）
- 判断基準: テストからimportされた場合はポート競合を避けるため実行しない

#### `app.inject()` のメリット
- 理解内容: HTTPサーバーを実際に起動せずにリクエストをシミュレートできる
- 判断基準: ポート競合なし・テストが速い・外部ネットワーク不要

#### ヘルパー関数を切り出した理由
- 理解内容: 各describeでテストデータの作成・削除が必要になるため重複コードを排除
- 実装での選択理由: describeをエンドポイントごとに分けてテスト対象を明確にしつつ、共通処理はヘルパー関数に集約
