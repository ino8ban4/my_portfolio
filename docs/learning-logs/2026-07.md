## Issue #34: Playwright導入 + E2Eテスト

### やったこと
- Playwright専用のDockerサービス(`e2e`)を追加し、投稿作成→一覧表示→削除のE2Eテストを実装

### 学び・理解した内容

**1. Alpine LinuxとPlaywrightの非互換**
- ChromiumはglibcベースでビルドされておりAlpine Linux(musl libc)では動作しない
- frontendの開発用コンテナ(Alpineベース)にPlaywrightを同居させず、E2Eテスト専用のコンテナ(`mcr.microsoft.com/playwright`イメージ、Debianベース)を分離して用意した
- 本番デプロイされるイメージ(軽量なAlpine)とテスト実行環境の設計思想は別物であるべき、という判断軸を得た

**2. バージョン一致の重要性**
- `@playwright/test`(npm)のバージョンと、Dockerイメージのタグ(ブラウザバイナリ・OS依存ライブラリ)が一致していないと、ホスト依存関係の検証エラーが発生する
- `v1.61.1-jammy`のように、公式が提示するバージョン-コードネームの組み合わせに正確に合わせる必要がある

**3. ロケーター戦略の使い分け**
- `getByLabel`: アクセシビリティの検証を兼ねる。フォームのlabel/input/textareaの紐付き(`htmlFor`/`id`)を厳密に書く動機になった
- `data-testid`: UI文言(開発者都合で変わりうる固定テキスト)に依存せず、操作対象の要素を安定して特定するために使用
- テキストベースのロケーター(`getByRole('link', {name})`): ユーザーが入力した可変データ(投稿タイトルなど)の検証に使う。UI文言とデータの性質の違いを区別する視点を得た

**4. テストデータのユニーク性**
- `Date.now()`でタイトルをユニークにしないと、複数回実行時に同名投稿が複数存在し、ロケーターがStrict Mode違反(複数要素にマッチ)でエラーになる

**5. 可変ID対応の正規表現マッチ**
- 詳細ページの`id`は自動採番される可変値のため、`toHaveURL(/\/posts\/\d+$/)`のような正規表現でパターンマッチさせ、具体的な値に依存しないテストにした

**6. 環境依存のデバッグ経験**
- `ENOENT: headless_shell not found`エラーの原因は、環境変数(`PLAYWRIGHT_BROWSERS_PATH`)の問題ではなく、ダウンロード自体が不完全だったこと
- `npx playwright install --force`で解決。「エラーメッセージの見た目(パス不一致に見える)」と「実際の原因(ファイル破損)」が一致しないケースがあることを実感した

## Issue #35: GitHub Actions CI(Vitest)

### やったこと
- `.github/workflows/blog-test-ci.yml`を新規作成(既存の古いCIファイルはパスが現行構成とズレていたため、技術的負債として別途整理予定)
- GitHub Actionsの`services`機能でPostgreSQLコンテナを一時起動し、Vitestテストを自動実行
- `prisma generate` → `prisma migrate deploy` → `npm test`の順で実行するワークフローを構築

### 学び・理解した内容

**1. GitHub Actionsの正体**
- 「ビルド機能」「テスト機能」が個別にあるわけではなく、指定した順にコマンドを実行できる使い捨てのLinux仮想マシンを借りられるだけの仕組み
- `jobs`は基本並列実行され、`needs`で依存関係(実行順序)を明示する

**2. `services`とDocker Composeの違い**
- どちらも「テスト対象と一緒にDBコンテナを起動する」という点では同じ発想だが、名前解決の仕組みが異なる
- Docker Compose: サービス名(`db`)で解決
- GitHub Actions services: `localhost`経由でアクセス
- この違いに気づかず、`vitest.config.ts`にDocker Compose用のホスト名(`db`)をハードコードしていたためCIで500エラーが発生した

**3. 環境ごとに変わる設定値は「環境変数優先、フォールバックはデフォルト値」で書く**
- `process.env.DATABASE_URL || 'postgresql://blog:blog@db:5432/blog'`のパターン
- 以前の`playwright.config.ts`の`baseURL`と全く同じ設計原則。ローカル/CI/将来のminikube環境、それぞれ接続先が変わっても、設定ファイル自体は書き換えずに済む

**4. `npm ci`と`npm install`の違い**
- `npm ci`は`package-lock.json`と完全一致させるクリーンインストール。CI環境の再現性確保に適している

**5. `prisma generate`と`prisma migrate deploy`の違い**
- `generate`: スキーマからPrisma Clientのコードを生成(型安全なクエリ用)
- `migrate deploy`: 実際にDBへマイグレーション(テーブル作成等)を適用

**6. トラブルシューティングの切り分け方**
- GitHub Actions自体の一時的な障害(Degraded状態、Actionsの実行遅延)に遭遇。実装ミスを疑う前に、外部要因(GitHub側のステータス)も確認する視点を得た
- `.env`ファイル内のコメントアウトされた行と、実際に有効な行を混同しそうになった。ファイルの中身を確認する際は「どの行が実際に有効か」を注意深く見る必要がある

## Issue #36: GitHub Actions CI(Playwright E2E)

### やったこと
- `.github/workflows/blog-e2e-ci.yml`を新規作成、PR作成時にDocker Compose環境全体(db/api/frontend/e2e)を起動しPlaywright E2Eテストを自動実行
- `depends_on: condition: service_healthy` + `healthcheck`で、apiが実際に使える状態になってからfrontendを起動する制御を実装
- 名前付きvolume(`api_node_modules`/`frontend_node_modules`)を復活させ、entrypoint.sh内でnpm installを実行することでCI環境でも正しくnode_modulesが用意されるようにした
- entrypoint.shにdotfiles有無の条件分岐を追加し、CI環境ではSSH/stow関連をスキップするようにした

### 学び・理解した内容

**1. depends_onの2段階**
- `depends_on: - api`(条件無し)は「apiコンテナの起動開始」を待つだけ
- `depends_on: api: condition: service_healthy`は「apiが実際にリクエストを処理できる状態(healthy)」になるまで待つ、より厳密な制御
- 前者だけでは、apiがまだ起動処理中(prisma generate等)の間にfrontendが先にfetchしてしまいECONNREFUSEDが発生する

**2. healthcheckのIPv4/IPv6問題**
- `wget http://localhost:3000/health`が、Alpine環境でlocalhostをIPv6(::1)として解決し、IPv4(127.0.0.1)でのみlistenしているアプリに接続できず失敗することがある
- 明示的に127.0.0.1を指定することで解決

**3. バインドマウントと名前付きvolumeの優先順位**
- `volumes: - ./api:/workspace`(バインドマウント)と`- api_node_modules:/workspace/node_modules`(名前付きvolume)を両方指定すると、より深い(具体的な)パスへのマウントが優先される
- CI環境ではホスト側(git checkout直後)にnode_modulesが存在しない(gitignore対象)ため、名前付きvolumeが無いとバインドマウントによってnode_modulesが空に上書きされてしまう
- 名前付きvolumeは「ローカルのnode_modulesを不要にする」という開発フロー(SSHでコンテナ内開発)にも合致する、正しい設計だった

**4. CI環境が「蓄積の無い、常にゼロからの状態」であることの意味**
- ローカル環境は、過去の蓄積(volumeの永続化、DBのデータ、手動で一度実行したprisma generateやmigrate等)によって、本来必要な初期化処理が省略されても動いてしまっていた
- CI環境は常にまっさらな状態から始まるため、この「隠れていた依存」が全て露呈する。今回発覚した問題(stow、prisma generate、node_modules、migrate deploy)は全てこの構造に起因していた

**5. entrypoint.shの環境分岐**
- `if [ -d /root/dotfiles/nvim ]; then ... fi`で、dotfilesが存在する(ローカル)場合のみSSH/stow関連を実行し、CI環境ではスキップする設計にした
- これは以前バックログに積んだ「entrypoint.shの将来的な分離(scripts/ディレクトリ化)」の簡易版としても機能した

**6. npm と npx の違い**
- `npm prisma generate`と`npx prisma generate`は別物。前者は存在しないnpmサブコマンドとして扱われエラーになる。npxはインストール済みパッケージの実行可能コマンドを呼び出すためのもの

## Issue: entrypoint.sh / docker-compose.ymlへの説明コメント追加

### 学び・理解した内容

**1. prisma generate と prisma migrate deploy は独立した処理**
- generateはPrisma Clientコード生成、migrate deployはDBへのテーブル反映で、互いに依存しない(実際に検証して確認)

**2. entrypoint.shは「ビルド時に1回」ではなく「コンテナ起動のたびに毎回」実行される**
- Dockerfileの`RUN`はビルド時1回のみ、`CMD`(entrypoint.sh呼び出し)はコンテナ起動ごとに毎回実行、という区別を再確認

**3. api_node_modulesの必要性を2つの理由に整理**
- (1) ホスト側node_modulesはgitignore対象のため初回実行前は空、ボリューム化しないとCI環境でこの空状態がそのまま反映されてしまう
- (2) entrypoint.shは起動のたびにnpm installするため、ボリューム化しないと毎回フルインストールになりローカルでの効率が悪化する
- 「後から上書きされる」のではなく「最初から保護された領域として確保される」という時系列の正確な理解に到達

**4. IF分岐の粒度の不一致に気づいた**
- dotfilesの有無で、本来別の関心事であるSSH設定まで一緒に判定してしまっている問題を発見。FIXMEコメントとして記録、将来のリファクタ(scripts/分離)対象に位置づけた

## Issue: api schemas/ディレクトリへのスキーマ定義分離

### やったこと
- `api/src/schemas/post.schema.ts`を新規作成
- base(内部材料、exportしない)と完成品(routes側が使う、exportする)を分離する設計を採用
- スプレッド構文(`...basePostBodySchema`)で、POST/PUTのbody差分(requiredの違い)を管理
- routes/posts.tsから、schema定義を分離してimportする形にリファクタ

### 学び・理解した内容

**1. Fastifyのschemaキー(params/body等)はFastify自身が定めた固定キーであり省略・変更不可**
- 一方、その中身(値)は変数として切り出し、再利用可能な部品にできる

**2. exportの有無で「内部材料」と「外部から使う完成品」を区別する設計**
- 呼び出し側(routes/posts.ts)は、中身がparamsかbodyかを意識せず、完成品の名前をimportするだけで済む
- 「複雑さを1箇所(schemaファイル)に閉じ込め、使う側から見えなくする」という関心の分離の実践

**3. スプレッド構文による差分管理**
- 共通の土台(properties等)をbaseとして持ち、エンドポイントごとに異なる部分(required)だけを個別に定義することで、保守性の高いコードになる

### 学び・理解した内容

- `<Component>テキスト</Component>`の書き方は、valueのような属性で渡すより、複雑な中身(JSXの組み合わせ)にも対応でき、HTML標準の書き方とも一貫性がある

**2. Linkとform+Server Actionの使い分け**
- 単なるページ遷移(処理を伴わない)はLink、データ変更を伴う操作(削除・更新)はform+Server Actionを使う、という判断基準を整理した

**3. JSXでの変数展開はクォート無しの波括弧`{}`のみ**
- `defaultValue='{post.title}'`(クォートで囲む)は文字列そのものとして扱われてしまい、`defaultValue={post.title}`が正しい

## Git/GitHubに関する理解の整理

- `origin`はローカルのディレクトリではなく、リモートリポジトリ(GitHub)につけられた「あだ名」。複数のリモートを持つ場合に区別するための名前で、`origin`自体に特別な技術的意味はない
- `origin/feature/xxx`はローカル内部の「リモート追跡ブランチ」の表記であり、リモート側の実際のブランチ名は接頭辞なしの`feature/xxx`。ブランチ削除コマンド(`git push origin --delete`)には後者を指定する
- 複数ブランチを並行作業させる場合、別ファイルを触っていればコンフリクトは起きないが、同じファイルの同じ箇所を編集していると、後からマージする側でコンフリクトが発生し、手動での解決(コンフリクトマーカーの編集)が必要になる
