# 2026-07 学習ログ

## Issue #34: Playwright導入 + E2Eテスト

### やったこと
- Playwright専用のDockerサービス(`e2e`)を追加し、投稿作成→一覧表示→削除のE2Eテストを実装

### 学び・理解した内容

**1. Alpine LinuxとPlaywrightの非互換**
- ChromiumはglibcベースでビルドされておりAlpine Linux(musl libc)では動作しない
- frontendの開発用コンテナ(Alpineベース)にPlaywrightを同居させず、E2Eテスト専用のコンテナ(`mcr.microsoft.com/playwright`イメージ、Debianベース)を分離して用意した
- 本番デプロイされるイメージ(軽量なAlpine)とテスト実行環境の設計思想は別物であるべき、という判断軸を得た

**2. バージョン一致の重要性**
- `@playwright/test`(npm)のバージョンと、Dockerイメージのタグ(ブラウザバイナリ・OS依存ライブラリ)が一致していないと、ホスト依存関係の検証エラーが発生する
- `v1.61.1-jammy`のように、公式が提示するバージョン-コードネームの組み合わせに正確に合わせる必要がある

**3. ロケーター戦略の使い分け**
- `getByLabel`: アクセシビリティの検証を兼ねる。フォームのlabel/input/textareaの紐付き(`htmlFor`/`id`)を厳密に書く動機になった
- `data-testid`: UI文言(開発者都合で変わりうる固定テキスト)に依存せず、操作対象の要素を安定して特定するために使用
- テキストベースのロケーター(`getByRole('link', {name})`): ユーザーが入力した可変データ(投稿タイトルなど)の検証に使う。UI文言とデータの性質の違いを区別する視点を得た

**4. テストデータのユニーク性**
- `Date.now()`でタイトルをユニークにしないと、複数回実行時に同名投稿が複数存在し、ロケーターがStrict Mode違反(複数要素にマッチ)でエラーになる

**5. 可変ID対応の正規表現マッチ**
- 詳細ページの`id`は自動採番される可変値のため、`toHaveURL(/\/posts\/\d+$/)`のような正規表現でパターンマッチさせ、具体的な値に依存しないテストにした

**6. 環境依存のデバッグ経験**
- `ENOENT: headless_shell not found`エラーの原因は、環境変数(`PLAYWRIGHT_BROWSERS_PATH`)の問題ではなく、ダウンロード自体が不完全だったこと
- `npx playwright install --force`で解決。「エラーメッセージの見た目(パス不一致に見える)」と「実際の原因(ファイル破損)」が一致しないケースがあることを実感した
