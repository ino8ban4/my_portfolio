# 2026年11月 学習ログ
## 11/23 #60 予算超過をきっかけに、EC2を自動停止する(SNS + Lambda)

(要補完: ブロック②③を実施した日付。ここでは、再テストを行った11/23にまとめて記録)

### やったこと
1. 構成: Budgets → SNS → Lambda → EC2 停止(タグ `AutoStop=true` かつ running のみ)
2. plan(10リソース) → apply → 手動テスト → destroy。destroy 後に、残りがないことを確認
3. destroy 後に、Lambda が自動で作った CloudWatch の log group だけが残っていたため、手動で削除

### 学んだこと
- 権限は、IDベースとリソースベースの2種類
  - IDベース: 実行する側(ロール)に付ける。「何を実行してよいか」
  - リソースベース: 呼ばれる側に付ける。「誰が使ってよいか」
- 今回の構成での分類
  - Lambda の実行ロールのポリシー: IDベース(EC2の停止、ログ出力)
  - SNS のトピックポリシー: リソースベース(Budgets が Publish してよい)
  - `aws_lambda_permission`: リソースベース(SNS が Lambda を Invoke してよい)。名前は permission だが、実体は Lambda に付くリソースベースポリシー
  - assume role(信頼ポリシー): ロールに付くリソースベースポリシー
- 判断のコツ: 入口(誰が Lambda を呼ぶか)は Lambda に `aws_lambda_permission`。出口(Lambda が何を呼ぶか)は実行ロール
- Budgets や SNS はAWSのサービスで、自分のアカウントにロールを持たないため、受ける側に「このサービスなら OK」と書く
- IAM の condition(`aws:ResourceTag/AutoStop`)は許可を絞るもの。コードのフィルター(探す)とは別の、止められる範囲の上限(安全柵)
- `(known after apply)` の境目
  - コードに書いた値や、既存のものを data が読む場合: plan で見える
  - これから作る resource の値(ARN や ID など)、およびそれを参照する式: apply まで不明
  - 判断の軸: 「その式が、まだ作っていないリソースを参照しているか」
  - `data "aws_caller_identity"` は、今の認証情報の持ち主を返す(ラベルの "me" は名前に過ぎない)
- plan は差分の予定表を計算するだけ。実際に作れるか(権限・名前の重複・上限)は apply で初めて分かる
- 空リストで `stop_instances` を呼んでも、DryRun で `DryRunOperation`(実行すれば成功する)になる。何も止まらない。ただし API によって空リストの意味は違うので、都度確認する
- EC2 には、インスタンスに付けるリソースベースポリシーがない
  - 制御は、呼ぶ側のIDポリシー、条件、SCP などで行う
  - EC2 に IAM ロールを付けなければ、AWS の API 権限はない。侵入されたときの被害の上限は、付けたロールの権限
  - 層を分ける: ネットワーク層(セキュリティグループ)と、コントロールプレーン層(IAM)

### つまずき
- 変数の参照を引用符で囲んだ。ハイフン入りの変数名にした(参照は引用符なし、名前はアンダースコア)
- `.terraform` のプロバイダバイナリが壊れた → `rm -rf .terraform` のあと `terraform init`
- apply の二重実行や Ctrl-C で state lock が残った → プロセスを確認して終了させ、`force-unlock <ID>`(`-lock=false` は使わない)
- Budgets のメールが届かなかった → 宛先が確認待ち(Pending)で、メールは迷惑メールフォルダにあった
- destroy で消えない log group が残った → 次回は `aws_cloudwatch_log_group` を Terraform で管理し、保持期間を設定する

### 理解テスト
- 1回目: 20%(1/5)
- 解説と再質問のあと、新しい問題で再テスト: 60%(3/5)。合格ライン80%は未達
- 間違えた点: `aws_lambda_permission` と実行ロールの混同、「plan が通れば apply も成功する」の誤解
- 記述での確認(S3 → Lambda → DynamoDB の許可の置き場所)は、自分の言葉で説明できた
- 数日後に、新しい問題で再テストする

### 弱点
- `aws_lambda_permission` と実行ロールの区別
- `(known after apply)` の境目(data が既存を読むのか、これから作るものを参照するのか)
- plan と apply の役割の違い

### 残課題
- 再テスト(80%)
- Terraform の実行の安全性(ローカルコンテナ＋プロジェクトごとのロール、OIDC での CI、`allowed_account_ids`)
- EventBridge Scheduler との比較
- `aws_cloudwatch_log_group` と保持期間の管理
