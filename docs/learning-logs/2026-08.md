## 8月: 自前K8s(kubeadm)構築 - 環境準備編

### 決定事項の経緯
- EKS(コントロールプレーン固定費 月$73)は予算(2,000〜3,000円)と相容れず断念
- ECSも検討したが、Platform Engineer職の市場価値としてK8sの汎用性を優先し、
  自前kubeadmクラスタ(EC2 2台構成)を選択
- 理由: 「fundamentals before abstractions」の原則。EKS/minikubeが隠していた
  コントロールプレーンの中身(API Server/etcd/Scheduler/Controller Manager)を
  自分の手で構築して理解する

### インフラ構成
- VPC 1つ + パブリックサブネット1つ(NAT Gateway回避、コスト優先)
- EC2 2台(t3.medium, Ubuntu 24.04 LTS): k8s-control-plane, k8s-worker
- セキュリティグループ共用(SSH:22, API Server:6443, etcd:2379-2380,
  kubelet:10250, Scheduler/Controller Manager:10251-10252, NodePort:30000-32767)
- IAMユーザー`k8s-learning`(EC2FullAccess + VPCFullAccess のみ、Adminキーは使わない)

### 運用ルール
- 作業終了時は「停止(stop)」、学習完了後に「削除(terraform destroy)」の1回のみ
- 停止中の課金: EBS代のみ(20GB×2台で月500円弱)。コンピュート代はゼロ
- パブリックIPは起動のたびに変わる → 毎回コンソールで確認
- テザリング等でグローバルIPが変わる場合、セキュリティグループの「マイIP」を
  再設定する必要がある(`curl -4 ifconfig.me`でIPv4を明示的に取得すること)

### 各ノードで実行したセットアップコマンド(コントロールプレーン/ワーカー共通)

\`\`\`bash
# パッケージ更新
sudo apt update && sudo apt upgrade -y

# スワップ無効化(Kubernetesの必須要件)
sudo swapoff -a
sudo sed -i '/ swap / s/^\(.*\)$/#\1/g' /etc/fstab

# containerdインストール + systemd cgroup設定
sudo apt install -y containerd
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sudo systemctl restart containerd
sudo systemctl enable containerd

# kubeadm/kubelet/kubectl インストール(v1.31固定)
sudo apt install -y apt-transport-https ca-certificates curl gpg
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.31/deb/Release.key | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.31/deb/ /' | sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo apt update
sudo apt install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
\`\`\`

### 理解の証明

**なぜスワップを無効化するか**
Kubernetesはコンテナごとのメモリ使用量を厳密に保証する設計のため、
スワップでメモリ不足をごまかせる状態だと`kubeadm init`自体が失敗する。

**なぜ`SystemdCgroup = true`が必要か**
cgroup(Linuxのリソース制限機構)の管理方式には systemd方式 / cgroupfs方式 の2種類があり、
containerdとkubeletで方式がズレると、リソース管理の認識不一致で原因不明の不安定動作を招く。
kubelet側・containerd側の両方をsystemd方式に揃える必要がある。
これはminikubeが`minikube start`一発で自動設定していた部分。

**`tee`コマンドを使う理由**
`sudo command > file` は `>` のリダイレクト自体がシェルの処理のため sudo 権限が効かず、
書き込み権限エラーになる。`command | sudo tee file` にすることで、
tee自体にsudo権限を持たせてファイル書き込みを行う。

**セキュリティグループのIPトラブル対処**
`curl ifconfig.me` はIPv6環境だとIPv6を返すことがあるため、
AWSのセキュリティグループ(IPv4前提)に設定する際は `curl -4 ifconfig.me` で
明示的にIPv4を取得する必要がある。

## 8月: 自前K8s(kubeadm)構築 - クラスタ構築・完了編

### 今回のゴール
コントロールプレーンの`kubeadm init`後、Podネットワーク導入・ワーカーの`kubeadm join`・
nginxの外部公開までを完了させ、Issueをクローズする。

### 作業の流れとトラブルシューティング

**1. preflightエラーの解消(コントロールプレーン)**
`kubeadm init`実行時に以下2点でエラー:
- `conntrack not found` → `sudo apt install -y conntrack`
- `ip_forward contents are not set to 1` → `sudo sysctl net.ipv4.ip_forward=1`
  (恒久化は `/etc/sysctl.conf` に追記 + `sudo sysctl -p` で反映確認)

**2. ホスト名の設計ミスと再構築**
`kubeadm init`を実行した後で、ノード名がプライベートIP由来
(`ip-172-31-xx-xx`)になっていることに気づいた。ホスト名は
`kubeadm init`より前に設定しておく必要があるため、両ノードとも
`sudo kubeadm reset -f` でリセットし、
`sudo hostnamectl set-hostname k8s-control-plane` /
`k8s-worker` を先に設定してから再度 `kubeadm init` を実行。

**3. ワーカー側で誤って`kubeadm init`を実行**
`join`ではなく`init`を実行してしまい、ワーカー側も独立したクラスタの
コントロールプレーンになってしまっていた(`kubectl get nodes`が
ワーカー側でも応答することで発覚)。両ノードとも再度リセットして対応。

**4. Podネットワーク(Calico)の導入**
\`\`\`bash
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.28.0/manifests/calico.yaml
\`\`\`
導入後、コントロールプレーンが`NotReady`→`Ready`に変化することを確認。

**5. `kubeadm join`のタイムアウト**
ワーカー側で`join`が`[preflight] Running pre-flight checks`のまま
進まず停止。原因はセキュリティグループの6443番ポートの「ソース」が
自分のPCのグローバルIP(マイIP)にのみ絞られており、ワーカーの
プライベートIPからの通信を許可していなかったため。
対処: 6443, 2379-2380, 10250番のソースに「セキュリティグループ自体」
を追加(同一SG内のインスタンス間通信を許可する設定)。

**6. NodePortでの外部アクセス不可**
nginxをService(NodePort)で公開したが、セキュリティグループで
30000-32767番が未開放だったためアクセスできず。追加して解消。

**7. テザリング環境でのIP変動**
作業環境によってグローバルIPが変わり、セキュリティグループの
「マイIP」設定とズレて接続不能になる現象が複数回発生。
`curl ifconfig.me`はIPv6を返すことがあるため、
`curl -4 ifconfig.me`でIPv4を明示的に取得して都度更新する運用で対応。

### 最終成果
- 2ノード(`k8s-control-plane`, `k8s-worker`)とも`Ready`状態
- nginxをDeployment + Service(NodePort)でデプロイし、
  `http://<ワーカーのパブリックIP>:<NodePort>` で外部アクセス確認済み

### 理解の証明

**理解内容**
- コントロールプレーンには4つの主要コンポーネント(API Server/etcd/
  Scheduler/Controller Manager)があり、それぞれ窓口・台帳・配置決定・
  監視修正の役割を担う
- コントロールプレーンには`NoSchedule`のTaintが標準でついており、
  これによりアプリのPodがコントロールプレーンに配置されるのを防いでいる
- Pod配置はSchedulerが自動決定するが、複数プロダクトが同居する場合は
  Taint/Toleration、ResourceQuota、NetworkPolicy等で意図的に制御できる
- 「自前運用の大変さ」の本質は初期構築の手間ではなく、
  単一障害点であるコントロールプレーンの冗長化・etcdバックアップ・
  証明書ローテーション・バージョンアップという**継続的な運用責任**
- kubeadmとEKSの違いは技術(共にKubernetes)ではなく、
  この継続的な運用責任を自分が負うか、AWSが肩代わりするか、という点

**判断基準**
- EKS(固定費$73/月)は予算と合わず、K8sの汎用性(転職市場での価値)を
  優先して自前kubeadmを選択
- 「fundamentals before abstractions」の原則に基づき、
  minikube/EKSが隠している部分を自分の手で構築することを優先

**実装での選択理由**
- Pod network CIDR(10.244.0.0/16)は、VPCのCIDR(10.0.0.0/16)と
  重複しない値として、Calicoのデフォルト慣習値を採用
- セキュリティグループはノード間通信のソースを「セキュリティグループ自体」
  に設定することで、動的なプライベートIPに依存しない構成にした

## 8月: BlogAPI on minikube - frontend編・ディレクトリ整理

### 今回のゴール
frontend(Next.js)をminikube上で動かし、db + api + frontend の3層すべての疎通を確認する。

### 作業の流れ

**1. frontend用の本番Dockerfile新規作成**
frontendには`Dockerfile.dev`(開発用、Neovim/tmux込み)しか存在せず、本番用の`Dockerfile`は
初めて作成した。Next.jsの`output: 'standalone'`モードを`next.config.ts`に追加し、
マルチステージビルド(deps → builder → runner)で軽量化。
非rootユーザー(`nextjs`)で実行し、最終イメージは304MB(旧`latest`は390MB)。

**2. ローカル(Mac)でのビルド事故未遂**
`npm run build`をMac上で直接実行し、`lightningcss`のネイティブバイナリ不一致で失敗。
`node_modules`はDocker Volumeとして切り出されており(ローカル環境を汚さない設計)、
誤って`rm -rf node_modules`しかけたが、実行前に気づいて回避。
本番ビルドの確認は必ずコンテナ内(`ssh blog-frontend-dev`経由)で行うべきだった。

**3. frontendコンテナのネットワーク異常**
`docker inspect blog-api-1`で確認したところ`"Networks": {}`(空)になっており、
apiコンテナがDocker Composeのデフォルトネットワークに参加していなかった。
`docker compose down && docker compose up -d`で解消。

**4. K8s Deployment/Serviceのタイポ・実装ミス(複数回)**
- `matchLabels`のタイポ、`template`の階層ミス(DBの時と同じパターン)
- Service作成時、`metadata: blog-frontend`のように`name:`キーを書き忘れる
- `-port:`(ハイフン後スペース抜け)、`targetPort: 30001`(桁数タイポ)

**5. ポート設定の重要な学び(今回のヤマ場)**
NodePort経由でアクセスしても繋がらず、以下の順で原因を切り分けた:
- `kubectl logs`で確認すると`http://...:3000`でリッスンしていた(3001ではなく)
- Next.js standaloneモードの`server.js`は、`entrypoint.sh`の`-p 3001`のような
  コマンドライン引数を一切見ない。**`PORT`環境変数でのみポート制御される**
- `PORT: "3001"`を追加後も、Pod内`localhost`へのwgetが失敗
  → `/proc/net/tcp`で確認すると実際は`10.244.x.x:3001`という**Pod自身のIPにのみ**バインド
  → standaloneモードは`HOSTNAME`環境変数でバインドアドレスを制御する
  → `HOSTNAME: "0.0.0.0"`を追加して解消

**6. localhostのIPv6解決問題**
Pod内から`wget http://localhost:3001`が`Connection refused`。
`127.0.0.1`を明示すると成功。以前apiのhealthcheckで遭遇したのと同じ、
`localhost`がIPv6(`::1`)に解決される問題だった。

**7. minikube Dockerドライバー特有のNodePort制約**
Pod自体へのアクセス(一時Pod経由)は成功するのに、`minikube ip:NodePort`への
外部アクセスだけ失敗する状態が発生。`minikube profile list`でDockerドライバーと判明。
macOS + Dockerドライバーの組み合わせでは、NodePortへの直接アクセスができないことがあり、
`minikube service <name> --url`でトンネル経由のURLを取得する必要がある
(このコマンドは実行したターミナルを専有し続ける必要がある)。

**8. k8s/app/ディレクトリのリファクタリング**
以前バックログに積んでいた「db-*.yaml, api-*.yaml のプレフィックス方式から
サブディレクトリ方式へ」を、このタイミングでまとめて実施。
`git mv`は「まだ一度もコミットしていないファイル」には使えないと分かり、
通常の`mv`で移動 → Gitが自動的に「rename」として検知してくれることを確認。

### 最終成果
- db + api + frontend、3層すべてがminikube上で`Running`、`minikube service --url`経由で
  疎通確認済み
- k8s/app/ ディレクトリを db/, api/, frontend/ のサブディレクトリ構成に整理

### 理解の証明

**Service/Endpoints/Podの関係**
- Service(ClusterIP)自体は固定の仮想IPを持つだけで、「どのPodに転送するか」という
  情報は自分の中に持たない
- 実際にPodのIP一覧を管理しているのは`Endpoints`という**独立したKubernetesリソース**
  (一般名詞の「エンドポイント」ではなく、`kubectl get endpoints`で見える実体)
- Endpoints Controllerがpodの増減を監視し、etcdに最新のPod IP一覧を書き込み続けることで、
  Podが再作成されてもService自体を変更する必要がない設計になっている

**トラブルシューティングの4層モデル**
今回実践した切り分け手順を、一般化して整理:
1. Pod自体(アプリが正しいポート/アドレスでlistenしているか) — `kubectl logs`, `kubectl exec`
2. Endpoints(Service→Podの紐付けが正しいか) — `kubectl get endpoints`
3. Service(ClusterIP) — `kubectl get svc`
4. 外部アクセス(NodePort) — `curl`, `minikube service --url`
内側の層から確認していくことで、問題を効率よく切り分けられる。
このうち層4の「Dockerドライバー特有の制約」はminikube固有の話で、
AWS(自前kubeadm)やEKSでは発生しない。

**CKAとの関連**
CKAのTroubleshootingドメイン(配点約30%)は、まさに今回実践した「ラベル不一致」
「ポート設定ミス」「段階的な切り分け」のパターンそのもの。CKAはドキュメント参照可の試験のため、
知識の暗記よりも「どの順番で確認するか」という手順の体得が評価される。
