## 9月: AWS(自前kubeadm)ネットワーク障害の切り分け ― IPIPとSG

### 今回のゴール
ArgoCDのApplicationが`Unknown`のまま解決しない原因を特定し、同期状態に戻す。
エラーは「argocd-redisの名前解決がi/o timeout」。

### 作業の流れ
エラー文を分解し、「名前解決の段階で止まっている」点から、下位レイヤーへ順に潰した。

1. CoreDNSのPod・ログ・Service・Endpoints → 異常なし
2. 別の汎用ドメインでも名前解決が失敗 → argocd-redis固有ではなく全体の問題と判明
3. CNI(Calico)のBGPピアリング → 確立済みで正常
4. 別ノード上のPod間でpingを直接確認 → 100%パケットロス
   (経路情報は正常なのに、実データが届いていない)
5. CNIのカプセル化方式を確認 → IPIP
6. AWSのセキュリティグループに、IPIP(IPプロトコル番号4)の許可がなかった
7. 許可を追加し、下位から逆順(ping → 名前解決 → ArgoCD同期)に再検証して回復

### 最終成果
- 原因: SGにIPIPの許可がなく、ノードをまたぐPod間通信がすべて破棄されていた
- 修正: SGにプロトコル4の許可(自己参照)を追加
- 結果: Pod間疎通と名前解決が回復し、ArgoCDが同期状態になった

### 理解の証明

**理解内容**
- BGPは経路情報の交換(制御プレーン)、IPIPは実データの転送(データプレーン)で
  別レイヤー。片方が正常でも、もう片方が止まれば通信は失敗する
- IPプロトコル番号はTCP/UDPの「ポート」とは別のL3の区分。IPIPにポートの概念はない
- 「名前解決のi/o timeout」は、DNSが答えなかったのではなく、
  問い合わせのパケットが相手に届いていない場合がある
- カプセル化を決めるのはKubernetesではなくCNI。
  Kubernetesは「NATなしでPod同士が通信できること」を要求するだけ
- EKSのVPC CNIはPodにVPCの実IPを割り当てるため、この問題は発生しない

**判断基準**
- DNS障害に見えても、まず下位(Pod間の到達性)を疑う。
  上位のCoreDNS設定から疑うと時間を浪費しやすい
- 原因は仮説の段階では「推定」と扱い、修正後の疎通回復で確定させた

**実装での選択理由**
- SGのソースを自己参照にしたのは、8月の構成と揃え、動的なプライベートIPに依存しないため

## 9月: BlogAPI デプロイ完了まで ― ストレージ・イメージビルド・CD構築

### 今回のゴール
`blog-api` / `blog-frontend` / `blog-postgres`をすべてRunningにし、
ArgoCDのApplicationをSynced / Healthyにする。
あわせて、イメージのビルドとGHCRへのpushをCDで自動化する。

### 作業の流れ
ネットワーク復旧後に、3つのPodが別々の原因で動いていないことが分かった。

| # | 症状 | 原因 | 対応 |
|---|---|---|---|
| 1 | blog-postgresがPending | PVCが要求するStorageClassがクラスタに存在せず、PVも未適用だった | PVを手動で適用(暫定) |
| 2 | blog-api/frontendがImagePullBackOff | GHCRにarm64のイメージしかなかった(Mac上の手動ビルドが原因) | CDでamd64をビルド |
| 3 | CDのビルドが失敗 | Dockerfileがロックファイルを使わず、npm installが内部エラー | npm ciとロックファイルのCOPYに変更 |
| 4 | frontendのビルドが失敗 | ビルド時のプリレンダリングで、存在しないAPIホストにfetchしていた | 該当ページを動的レンダリングに指定 |
| 5 | arm64のビルドが17分以上進まない | QEMUエミュレーションが遅い | amd64のみに絞り、QEMUのステップを削除 |
| 6 | frontendのpushが拒否される | GHCRパッケージにリポジトリのActions権限がなかった | パッケージ側で権限を追加 |

CDは、CIとは別のワークフローとして新規に作成した。

- CI(テスト)はPRとmainへのpushで動き、CD(GHCRへのpush)はmainへのpushのうち
  api/frontendの変更を含む場合だけ動く
- 手動実行も可能
- ワークフローファイル自体の追加はパスの条件に合わないため、初回は手動で実行した

### 最終成果
- 3つのPodがすべてRunning、ArgoCDがSynced / Healthy
- イメージのビルドとpushがCDで自動化された(amd64のみ)
- 暫定対応として、PV/PVCは手動管理のまま残っている

### 理解の証明

**理解内容**
- ビルドしたマシンのCPUアーキテクチャが、そのままイメージの対象になる。
  マニフェストに実行ノードのアーキテクチャ向けのエントリがないと、pullに失敗する
- StorageClassは「メニュー」、Provisionerは「実際に作る側」。
  minikubeは両方を標準で用意していたが、自前kubeadmには存在しない
- `npm ci`はロックファイルの内容を厳密に再現し、食い違いはエラーにする。
  Dockerビルドやパイプラインでは`npm ci`、依存の追加・更新は`npm install`と使い分ける
- Next.jsでは、コンポーネント内で直接fetchするページはビルド時に実行される。
  実行時のみ動く処理(フォーム送信など)や、動的なパスのページは対象外
- Dockerビルドは失敗したら即停止する。Kubernetesの再起動の仕組みは、
  起動後のクラッシュにのみ働き、ビルドの失敗には働かない
- ビルドした場所(runner)は毎回破棄されるため、キャッシュを明示的に設定しないと、
  毎回最初からビルドになる
- GHCRのパッケージには、pushを許可するリポジトリを個別に登録する必要がある。
  手動push時の個人トークンでは不要だったが、ActionsのトークンではこのAccess設定が必要

**判断基準**
- 本番ノードがamd64のみなので、arm64のビルドは不要と判断した。
  実務でも、本番で動くアーキテクチャだけをビルドするのが一般的
- 手元のMacで動作確認するだけなら、pushしないローカルビルドで足りる
- 「PV手動管理」は学習用の暫定。クラウドでは、プロバイダ純正のProvisionerを
  使うのが前提で、StorageClassのYAMLは性質を定義するだけ

**実装での選択理由**
- CDをCIと分けたのは、テストは変更を確認するため、イメージのpushは
  本番に使うものを作るためで、動かすべきタイミングが違うから
- CDのトリガーをmainへのpushに限ったのは、マージ前のコードのイメージを
  本番用のレジストリに置く意味がないため

### 次にやること
- PV/PVCの手動管理を、動的プロビジョナーに置き換える
- CDのビルドキャッシュを有効化する
- CIのテストジョブのnpm installを、npm ciに揃える

## 9月〜10月: Terraform基礎 ― init → plan → apply → destroyとAWSプロファイル整理

### 今回のゴール
Terraformの基本サイクルを一周し、AWS認証の整理を済ませる。
題材はBlogAPI環境から切り離した使い捨てのS3バケット1つ。

### 作業の流れ
1. 学習用のディレクトリを、既存のplatform-engineering配下に作成
2. providerを設定して`init`を実行し、`plan`を確認
   (リソースが無い状態では「変更なし」になる)
3. S3バケットを定義し、`plan`で「1つ作成予定」を確認
4. 認証がrootに見えたため、`apply`の前に中断して方針を決め直した
5. AWS CLIのプロファイルを整理(後述)してから、`apply`→確認→`destroy`

### AWS認証の整理
- 当初、認証が「rootユーザー」に見えたため、`apply`の前に作業を止めた
- 方針: 権限を細かく分けたIAMユーザーは作らず、既存のadmin権限のIAMユーザーを使う
- 新しいプロファイルにadminの認証情報を登録し、`default`はダミー値に置換した
  (`--profile`の付け忘れが、エラーで止まるようにするため)
- クラスタの起動・停止スクリプトは、スクリプト内でプロファイルを指定する形に修正
- 確認の結果、rootのアクセスキーは存在しなかった。
  当初の「rootで動いている」という判断は読み違いの可能性が高い

### 最終成果
- `init` → `plan` → `apply` → 実体確認 → `destroy`を一周した
- AWS上にバケットは残っていない
- 認証の指定が、環境変数1つで明示的に切り替わる状態になった

### 理解の証明

**理解内容**
- `plan`はコード・state・実際のAWSの3つを突き合わせて差分を計算するだけで、
  変更はしない。コンパイルに近いのは`validate`(クラウドには問い合わせない)
- `tfstate`は、コード上のリソースとAWS上の実体を結ぶ台帳。
  無くなると、作ったものを管理できなくなり、`destroy`も効かない
- `plan`に出る`(known after apply)`は、作成後にしか決まらない値
- `~>`は「メジャーバージョンを固定し、マイナーは自由」を表す制約。
  ロックファイルで、実際に使うバージョンを固定する
- `VAR=値 コマンド`は、そのコマンド1回だけ環境変数を渡す書き方
- リソースの種類・引数名はproviderが決めており、ラベルはコード内だけの呼び名

**判断基準**
- ロックファイルはGit管理に含め、`.terraform/`とstateは含めない
- 権限を細かく分けるのは、扱うリソースが増えてからでよい。
  今は管理の手間のほうが大きい
- `default`をダミーにするのは、付け忘れを事故にせず、エラーで検知するため

**実装での選択理由**
- 題材をBlogAPI環境のimportではなく使い捨てのS3バケットにしたのは、
  `apply` / `destroy`に慣れる前に、動いている環境を巻き込まないため

### 次にやること
- stateをS3でリモート管理する(stateのロックの考え方も含む)
- 小さなEC2を作り、依存関係のあるリソースで`plan`の読み方を練習する
- その後にEKS検証へ
