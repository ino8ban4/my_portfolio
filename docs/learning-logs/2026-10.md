## 10/5 Terraform state のリモート管理(S3バックエンド)

### やったこと
1. stateバケットを AWS CLI で作成(Terraform外)し、バージョニングを有効化
2. main.tf の terraform ブロックに backend "s3"(bucket / key / region / encrypt / use_lockfile)を追加
3. `AWS_PROFILE=admin terraform init` で接続
4. apply → destroy で、S3上に state が書かれ、版が積み上がることを確認

### 学んだこと
- stateを置くバケットだけは、Terraform外で作る(卵ニワトリ回避)
- gitでstateを管理しない理由
  - 秘密情報が平文で入り、履歴に残る
  - lockがない(同時applyでstateが壊れる)
  - 最新のstateを取る作業が手作業になる
- planはコード・state・実体の比較。stateが古いと、誤った差分(他人が作ったリソースを「ない」と誤認)が出る。planは最新のstateであることまでは保証しない
- lock: use_lockfile = true で S3上に .tfstate.tflock を作り、終了時に削除する(Terraform 1.10以降。DynamoDBは不要)
- lineage はstateの系譜ID、serial は更新ごとの通し番号。別系譜や古いserialでの上書きを止める
- バージョニング: 上書きや削除のたびに古い中身が別の版として残る
  - `aws s3 ls` は最新版だけ。`aws s3api list-object-versions` で全版と削除マーカーが見える
  - 差分表示の機能はない。get-object --version-id で取り出して diff する
- apply版は2756バイト、destroy後は181バイト(resources が空)。serial 1 → 2
- backendブロックには変数が使えない

### 想定と違ったこと
- init時に「既存stateをコピーするか」の質問が出なかった。ローカルstateが空(resources: [])だったため。S3側の serial は 1 から始まった(ローカルは 4 だった)
- 空stateでの挙動のみ確認。中身のあるstateでの移行(-migrate-state)は未確認
- list-object-versions には .tflock の版(plan/apply/destroy の開始時に作られた分)も混ざる。Key を表示すると区別できる

### つまずき
- AWS_PROFILE=admin の付け忘れで `terraform state list` が 403(InvalidClientTokenId)。default をダミーにしてあるための意図した挙動
- AWS CLIのページャー(less)で出力が止まる。`q` で抜ける。`export AWS_PAGER=""` で無効化できる

### 理解テスト
- 選択式 80%(4問目「planとstateの関係」を間違えた)
- 記述: 「ローカルとリモートの比較」ではなく、「手元のstateが古いと誤った差分が出る」と整理し直した

### 残課題
- stateバケットのパブリックアクセスブロック、IAMの絞り込み
- state lock の競合の実演(2つ目のターミナルで同時apply)
- 中身のあるstateでの -migrate-state の確認

### 次回
- Terraformで小さなEC2を作る(依存関係のあるリソースで plan の読み方を練習)
- 休み(10/19から18日間)に Terraform・EKS をまとめて進める


## 10/19 TerraformでVPC・EC2を作る(依存関係とplanの読み方)

### やったこと
1. 新ディレクトリ ec2-basics を作り、backendのkeyを分けて init
2. VPC・パブリックサブネット → IGW・ルートテーブル・関連付け・SG → AMI(data)とEC2(t3.micro)の順に apply
3. state show と describe-instances で、stateと実体の両方を確認
4. destroy で7リソースを削除(state list も空)

### 学んだこと
- 参照(aws_vpc.main.id)が依存関係になる。作成順も削除順も、依存グラフから毎回計算される
- (known after apply) は、AWSが決める値と、未作成の依存先の値の2通り。作成済みの依存先はplan時点でIDが見える
- data ソースは読むだけ。plan時点で読み込まれ、作成数にも削除数にも入らない
- destroyは、使われていないものから、依存の逆向きに、並行して進む
- stateは、コードに書いていない属性(public_ip、arn、private_ip)も丸ごと保存する。秘密情報も入りうる
- Terraformで作るSGは、egressを書かないと全拒否になる(説明で学んだ。未検証)
- public_dns は null だった(VPCのenable_dns_hostnamesがデフォルトでオフ)

### 想定と違ったこと・訂正
- (known after apply) を依存関係だけの目印と説明していたのを、2通りの理由に訂正
- destroyは作成順の厳密な逆ではなく、並行して進む(関連付けとEC2が同時に開始)

### 残課題
- SSH接続、NAT Gateway、複数AZ、module化
- Budgetsアラート → EKS(作って、触って、その日のうちにdestroy)

## 10/21 AWS Budgets のコストアラート(Terraform)と、EKSの準備

### やったこと
1. budgets ディレクトリで、変数(variable)と tfvars を使い、月額上限 $20 の予算を作成(実績80%、予測100%の通知)
2. 通知を鳴らすため、-var で上限を一時的に下げて apply(~ その場の更新を確認)
3. eks-basics で、ネットワーク(2AZ)、IAMロール(クラスタ用・ノード用)、クラスタ、ノードグループのコードを書き、plan まで(15リソース)

### 学んだこと
- variable は宣言、tfvars は値。値は -var > tfvars > default の順で優先される。メールアドレスは tfvars に書き、gitには入れない
- validate は、スキーマと参照の整合性だけを調べる。属性名のtypoは見つかるが、引用符で囲んだ変数("var.xxx")は通る
- (known after apply) は、AWSが決める値と、未作成の依存先の値。data は plan 時点で読み込まれる
- Budgets は請求データの更新に依存し、通知は遅れる。通知は、状態が OK → ALARM に変わったときに送られる
- 新しい宛先は、確認メールのリンクで確認が済むまで、通知を受け取れない(Pending)

### つまずき
- limit_amount を引用符で囲み、変数名もハイフンになっていた(plan で気づいた)
- 確認メールが迷惑メールに入っていて、宛先が Pending のまま。通知が届かなかった
- リソース名の typo(publick_1、aws_availability_zone と複数形の違い)は、validate で見つかった
